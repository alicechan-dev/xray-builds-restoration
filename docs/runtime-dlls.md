# Runtime DLL Loading Map

Historical snapshot: S.T.A.L.K.E.R. X-Ray Build 1935.

This document records explicit `LoadLibrary` / `GetProcAddress` use, plugin-style DLL interfaces, and important runtime DLLs that must be placed beside the executable even when they are loaded by the Windows import table instead of by hand-written loader code.

## CMake Staging Rules

1. Put `XR_3DA.exe` and all engine-produced runtime DLLs in one directory, e.g. `build/bin`.
2. Always stage the engine-critical internal DLLs once they build: `xrCore.dll`, `xrCDB.dll`, `xrSound.dll`, `xrLUA.dll`, `xrGame.dll`, `xrCPU_Pipe.dll`, `xrRender_R1.dll`, and any directly linked support DLLs.
3. Stage `xrRender_R2.dll` when the R2 target is enabled; do not make R2 block the first R1 runtime bootstrap.
4. Treat `xrLauncher.dll`, `xrLC_Options.dll`, `xrEPropsB.dll`, `SciLexer.DLL`, and old editor DLLs as optional tool/editor phase artifacts.
5. Do not copy Windows system DLLs such as `d3d9.dll`, `DBGHELP.DLL`, `shell32.dll`, `comctl32.dll`, or .NET framework assemblies by default.
6. Prefer static vendored Ogg/Vorbis for the first CMake runtime unless preserving the original dynamic codec layout is a specific goal.
7. If using bundled OpenAL dynamically, build and stage `wrap_oal.dll`; decide separately whether to stage the router `OpenAL32.dll` or rely on the system/OpenAL runtime.
